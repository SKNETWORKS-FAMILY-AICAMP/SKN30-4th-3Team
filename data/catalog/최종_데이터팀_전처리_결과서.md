# 4차 프로젝트 V2 데이터팀 최종 전처리 결과서

## 1. 목적

본 문서는 4차 프로젝트 V2에서 데이터팀이 수행한 국내 공공데이터와 해외 보충 데이터의 수집, 품질 검증, 정규화, 청킹, 임베딩, Supabase 적재 결과를 하나로 정리한 발표 자료 참고용 문서이다.

기존 문서 두 개를 통합하였다.

- 국내 데이터: 농사로, 국립수목원, NCPMS, PSIS 등
- 해외 데이터: PlantSolve, EPPO, Perenual

## 2. 핵심 결과

- 식물 생육 중심의 기존 RAG를 텃밭 관리, 병, 해충, 농약 정보까지 확장하였다.
- 서로 다른 출처의 식물명은 `plant_catalog`, 표준국명, 검증된 이명, 학명 순으로 확인하여 대표명에 연결하였다.
- 농약 제품별 등록정보 13,158건을 1,168개 검색 그룹으로 정리하고 제품별 정확한 사용정보는 구조화 데이터로 보존하였다.
- 해외 데이터는 정규화·청킹·임베딩까지 수행한 뒤 품질을 재검토하여 PlantSolve 생육 정보 28건만 적재하고 EPPO·Perenual 데이터는 제외하였다.
- 마지막 NCPMS supplement 28청크와 해외 PlantSolve 28청크를 포함한 Supabase 적재량은 총 4,841청크이다.

## 4. 공통 전처리 파이프라인

```text
원본 수집
→ 출처·라이선스 확인
→ 식물명·학명 검증
→ 텍스트 정제
→ 공통 RAG JSONL 정규화
→ 문서 단위 청킹
→ 1,536차원 임베딩
→ 파일 구조·중복 검증
→ Supabase 적재
→ 식물별 데이터 coverage 재확인
```

### 4.1 단계별 산출물

| 단계 | 저장 위치 | 주요 산출물 |
|---|---|---|
| 원본 수집 | `data/raw`, `data/interim` | API 응답, JSON, JSONL |
| 검토·정규화 | `data/interim`, `data/interim/normalized` | 대표명 매핑, normalized JSONL, review JSONL |
| 청킹 | `data/processed` | `rag_chunks.*.jsonl` |
| 임베딩 | `data/processed` | `rag_chunks.*.embedded.jsonl` |
| 적재 | Supabase | `rag_sources`, `rag_chunks`, `psis_pesticide_chunks` |

## 5. 식물명 검증과 재검색

### 5.1 해결한 문제

출처마다 동일한 재배 대상이 다르게 기록되어 있었다.

```text
감귤 / 감귤나무
들깨 / 깻잎 / 들깨(잎)
사과 / 사과나무
오렌지재스민 / 오렌지쟈스민
```

이 이름을 그대로 사용하면 같은 식물의 생육·병해충·농약 문서가 서로 다른 식물로 검색된다.

### 5.2 검증 우선순위

```text
1. plant_catalog 대표명 정확 일치
2. API 결과 국명 정확 일치
3. 검증된 이명·표기 변형 일치
4. 학명 정확 일치
5. 모두 실패하면 unmatched로 분리
```

검색 결과가 없다는 이유로 이름이 비슷한 다른 식물을 자동 선택하지 않았다. 후보가 여러 개면 첫 결과를 채택하지 않고 정확한 국명 또는 학명으로 한 종을 확정할 수 있는 경우만 사용하였다.

### 5.3 국립수목원 재검색

생육 정보가 없는 식물을 별도 목록으로 추출한 뒤 국립수목원 API를 검색하였다.

```text
국명 검색
→ 정확 일치 여부 확인
→ 불일치·다중 후보는 review로 이동
→ 검증된 학명 입력
→ 학명으로 API 재검색
→ API 결과 국명·학명 재확인
→ plant_catalog 대표명으로 정규화
```

검색 이력에는 다음 값을 보존하였다.

| 필드 | 의미 |
|---|---|
| `query_name` | 최초 검색 대상 식물명 |
| `searched_term` | 실제 API 검색어 |
| `api_result_name` | API 결과 식물명 |
| `scientific_name` | 검증에 사용한 학명 |
| `catalog_name` | 서비스 최종 대표명 |
| `mapping_method` | 국명·이명·학명 등 연결 근거 |

### 5.4 PSIS 미일치 검색

대표명 검색으로 농약 결과가 없는 식물은 unmatched JSONL로 분리하였다.

```json
{
  "canonical_name": "대표 식물명",
  "search_aliases": ["검증 후보 1", "검증 후보 2"]
}
```

`search_aliases`는 표기 변형과 확실한 동의어만 등록하였다. 후보를 순서대로 검색하되 결과가 있다는 이유만으로 다른 식물을 자동 채택하지 않았다. 정확 결과가 확인된 항목은 다음 실행에서 unmatched 목록에서 제외되도록 구성하였다.

## 6. 텍스트 정제

### 6.1 제거 항목

- HTML 태그와 escape 문자
- 이미지 경로와 `src=?` 형태의 잔재
- 메뉴, 조회수, 콘텐츠 담당자 등 사이트 UI 문구
- `▶`, `①`, `•`처럼 장식과 순서 표시에만 사용되는 기호
- 본문에 반복된 제목과 식물명
- 월별 재배 달력과 생산 통계표가 깨진 문자열
- 이미지 위주이거나 의미 있는 텍스트가 거의 없는 문서
- 중복 공백과 불필요한 개행

### 6.2 보존 항목

생육 조건과 사용기준에 필요한 다음 정보는 삭제하지 않았다.

- 온도: `℃`, `°C`
- 길이·면적: `cm`, `㎝`, `㎡`
- 농도·비율: `%`, 배수
- 범위·크기: `~`, `×`

## 7. 출처별 전처리

### 7.1 농사로

- 개별 식물 재배 문서와 텃밭 전체 관리 문서를 분리하였다.
- 과수·채소 문서는 `plant_catalog`에 있는 식물을 중심으로 대표명을 통일하였다.
- 텃밭 공통 문서는 특정 식물명을 강제로 연결하지 않고 계획·농자재·모종 심기 등의 `section`으로 구분하였다.
- HWPX 농작업 일정은 XML 문단과 표를 재파싱하여 문장형 텍스트로 변환하였다.
- 구조가 깨진 달력·통계표와 텍스트가 거의 없는 이미지 중심 문서는 제외하였다.

### 7.2 국립수목원·KPNI

- 표준국명과 학명을 기준으로 식물명을 묶고 이명과 통용명을 alias로 보존하였다.
- 생육환경, 번식법, 형태, 재배 특징이 있는 상세 결과를 RAG 문서로 변환하였다.
- 동일 식물이 여러 검색명으로 수집된 경우 `doc_id` 기준으로 중복 제거하였다.
- 정확히 매핑되지 않은 이름은 억지로 학명을 부여하지 않고 검토 대상으로 남겼다.

### 7.3 NCPMS

```text
공식 작물 코드 목록
→ 병 목록 SVC01
→ 병 상세 SVC05
→ 해충 목록 SVC03
→ 해충 상세 SVC07
```

- 병 상세와 식물 관계는 `sick_key`로 결합하였다.
- 해충 상세와 식물 관계는 `insect_key`로 결합하였다.
- 검색 결과, 상세정보, 식물 관계를 별도 JSONL로 보존하였다.
- 이미지 필드를 제외하고 증상, 발생 조건, 피해, 생태, 예방·방제 내용을 정규화하였다.
- 공식 작물 코드와 연결되지 않거나 상세 키가 누락된 관계는 review로 분리하였다.
- 확정 진단이나 직접 처방으로 보이지 않도록 안전 태그를 포함하였다.

### 7.4 PSIS

```text
NCPMS·Supabase 식물 목록 준비
→ SVC01 농약 등록 목록 수집
→ 미일치 식물 별칭 검증
→ SVC02 제품 상세 수집
→ 작물 + 대상 병해충 + 용도로 그룹화
```

- 제품별 등록정보 13,158건을 1,168개 검색 그룹으로 축소하였다.
- 반복되는 등록 건수와 공통 안내 문구는 검색 본문에서 제거하였다.
- 제품명, 유효성분, 희석배수, 사용 시기, 수확 전 사용기한, 최대 사용 횟수, 독성, 업체 정보를 구조화하여 보존하였다.
- 중단 후 재실행할 수 있도록 목록 수집과 상세 수집을 분리하고 resume 방식을 적용하였다.

### 7.5 해외 3개 출처

#### PlantSolve

- 원본 생육·케어 데이터 98건을 정규화·청킹·임베딩하였다.
- 학명 일치, 빈 값, placeholder, 출처 조건을 재검토하였다.
- 품질을 통과한 식물 28종만 최종 Supabase에 반영하였다.

#### EPPO·Perenual

- EPPO 373건, Perenual 373건을 수집하였다.
- 병·해충 통합 데이터와 농약·방제자재 데이터를 서로 다른 파이프라인으로 분리하였다.
- 병·해충 청크 746건과 농약·방제 청크 746건을 생성하고 임베딩까지 수행하였다.
- 다수 문서가 식물별 고유 정보가 아닌 공통 템플릿 문구로 반복되어 검색 품질과 안전성이 떨어질 가능성을 확인하였다.
- 부정확하거나 일반화된 농약 처방이 노출될 위험을 고려하여 전량 Supabase 적재에서 제외하였다.

## 8. 공통 정규화 스키마

| 필드 | 역할 |
|---|---|
| `source_id`, `source_key` | 출처 식별과 `rag_sources` 연결 |
| `doc_id` | 원본 문서의 안정적인 고유 키 |
| `title`, `text` | 검색 결과 제목과 임베딩 대상 본문 |
| `category`, `section` | 생육·병·해충·농약 및 문서 구간 분류 |
| `crop_or_plant` | 식물명 정확 필터와 검색 |
| `symptom_keywords` | 증상 중심 검색 보조 |
| `url`, `publisher`, `collected_at`, `license` | 출처와 수집 이력 |
| `safety_tags` | 확정 진단·직접 처방 방지 |

안정적인 `source_id`, `doc_id`, `chunk_id`를 생성하여 같은 데이터를 다시 적재할 때 `chunk_id` 기준 upsert가 가능하도록 하였다.

## 9. 청킹

### 9.1 공통 원칙

- 서로 다른 식물 문서를 하나의 청크에 섞지 않았다.
- 긴 문서는 해당 문서 내부에서만 분할하였다.
- 문장 끝과 줄바꿈을 우선 경계로 사용하였다.
- 경계에서 문맥이 끊기지 않도록 overlap을 적용하였다.
- 너무 짧거나 의미 있는 문자의 비율이 낮은 청크는 제외하였다.
- 출처, 식물명, 카테고리, 안전 태그를 모든 청크 metadata에 유지하였다.

### 9.2 주요 청킹 기준

| 데이터 | 최대 글자 수 | overlap | 적용 이유 |
|---|---:|---:|---|
| NCPMS 병·해충 | 1,400자 | 160자 | 증상·발생조건·방제 구간을 독립적으로 검색 |
| 국립수목원 생육 | 약 1,400자 | 약 160자 | 형태·환경·번식 문맥 보존 |
| 농사로 텃밭 공통 관리 | 1,200자 | 140자 | 텃밭 관리 주제별 검색 |
| PSIS 농약 그룹 | 기본 2,200자 | 250자 | 제품명·성분 정보를 같은 검색 단위에 유지 |

NCPMS와 PSIS는 전용 청킹 코드를 사용하였다. 명시적인 `crop_or_plant`가 있는 경우 본문에서 식물명을 다시 추론하지 않아 잘못된 식물명이 metadata에 추가되는 문제를 방지하였다.

PSIS의 제품별 `registrations` 전체는 임베딩 본문에 반복하지 않고 별도 구조화 값으로 유지하였다.

## 10. 임베딩과 적재 구조

### 10.1 임베딩

- 청크의 `text`를 OpenAI 1,536차원 임베딩으로 변환하였다.
- 식물명, 출처, 카테고리는 metadata와 별도 컬럼에 보존하였다.
- 임베딩 전후 청크 수, 벡터 길이, 중복 `chunk_id`를 검증하였다.

### 10.2 기존 RAG 테이블

생육·텃밭·병·해충 데이터는 기존 검색 구조를 유지하였다.

```text
rag_sources
rag_chunks
```

- `rag_sources`: 기관, URL, 수집일 등 출처 정보
- `rag_chunks`: 본문, 임베딩, 식물명, 증상 키워드, metadata
- `chunk_id` 기준 upsert로 중복 방지

### 10.3 농약 전용 테이블

제품별 등록정보를 정확하게 보존하기 위해 별도 테이블을 구성하였다.

```text
public.psis_pesticide_chunks
```

| 컬럼 | 역할 |
|---|---|
| `crop_name` | 작물명 정확 검색 |
| `target_disease_pest` | 대상 병해충 검색 |
| `use_type` | 살균·살충 등 용도 |
| `text`, `embedding` | 자연어 검색 |
| `pesticide_names` | 제품명 배열 |
| `active_ingredients` | 유효성분 배열 |
| `registration_count` | 그룹 내 등록 건수 |
| `registrations` | 제품별 사용법·독성·업체 정보 |
| `metadata` | 출처와 안전 태그 |

자연어 검색은 관련 농약 그룹을 찾는 역할만 담당하고, 희석배수·사용 시기·횟수·독성은 `registrations`의 구조화 값을 사용하도록 분리하였다.

## 11. 품질 검증과 적재 결정

### 11.1 공통 검증

- 필수 metadata 누락 확인
- 중복 `doc_id`, `chunk_id` 확인
- 1,536차원 임베딩 확인
- NCPMS 상세 키와 식물 관계 키 확인
- PSIS `registration_count`와 실제 배열 길이 비교
- 미매핑 식물명과 검토 필요 관계 별도 분리
- Supabase 적재 후 식물별 생육·병·해충·농약 coverage 재집계

### 11.2 안전성 기준

- 병해충 정보는 확정 진단이 아닌 관찰 참고 정보로 태깅하였다.
- 농약은 제품 라벨과 최신 등록정보 확인이 필요하도록 안전 태그를 포함하였다.
- 템플릿 반복이 심하거나 특정 식물과의 관계가 불명확한 해외 병해충·농약 데이터는 적재하지 않았다.

## 12. 최종 Supabase 반영량

마지막 NCPMS supplement 28청크와 해외 PlantSolve 28청크를 모두 포함하였다.

PSIS 1,268개 중 1,168개는 농약 전용 `psis_pesticide_chunks`에 저장되어 있다. 나머지 데이터는 기존 `rag_chunks`에 저장되어 있다. KPNI 표준식물목록은 `plant_catalog` 정규화에 사용되므로 RAG 청크 수에는 포함하지 않았다.

## 13. 최종 결과

- 국내 공공데이터를 중심으로 생육·텃밭·병·해충·농약 검색 기반을 확장하였다.
- 표준국명·이명·학명 검증으로 출처 간 식물명 차이를 줄였다.
- 구조화 농약 데이터와 자연어 벡터 검색의 역할을 분리하여 정확도를 확보하였다.
- 해외 데이터는 파이프라인 완성 여부와 별개로 최종 품질 검토를 거쳐 적재 여부를 결정하였다.
- 한 채팅에서 식물 생육 관리, 병·해충 관찰 정보, 등록 농약 정보를 함께 조회할 수 있는 데이터 구조를 마련하였다.
